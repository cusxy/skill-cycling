# Release Plugin

Ты — процедурный skill публикации новой версии плагина. Ты работаешь inline
в основном контексте и выполняешь шаги релиза последовательно, не вызывая
субагентов.

## Входные параметры

- **Тип изменений**: `major` | `minor` | `patch` (SemVer). Если не указан —
  запроси у пользователя через `AskUserQuestion` с обоснованием на основе
  git log с предыдущего тега.
- **Release notes**: краткое описание изменений. Если не указаны —
  сгенерируй из `git log <prev-tag>..HEAD` и покажи пользователю на
  подтверждение.

## Definition of Ready

Перед началом релиза проверь:

- `dor-1`: Текущая ветка — `main`. Если нет — прекрати и сообщи пользователю.
- `dor-2`: Working tree чист (`git status --porcelain` пусто). Незакоммиченные
  изменения ЗАПРЕЩЕНО включать в релиз — это приведёт к несоответствию тега
  и реального состояния дерева.
- `dor-3`: Локальный `main` синхронизирован с `origin/main` (`git fetch` +
  сравнение). Отставание от upstream — блокер.
- `dor-4`: `agloom format --check` проходит без ошибок.
- `dor-5`: Определён тип изменений (`major`/`minor`/`patch`) и release notes.
- `dor-6`: Предыдущий тег найден (`git describe --tags --abbrev=0`) либо
  подтверждено, что это первый релиз.

## Шаги публикации

ТРЕБУЕТСЯ выполнять в указанном порядке. При ошибке на любом шаге —
прекратить и сообщить пользователю, не откатывая частично применённые шаги
автоматически.

1. **Вычислить новую версию**. Прочитать `plugin.yml`, взять текущее
   значение `version`, инкрементировать согласно типу изменений.
2. **Обновить `plugin.yml`**. Заменить `version: <old>` на `version: <new>`.
3. **Показать diff пользователю** и запросить подтверждение через
   `AskUserQuestion` перед коммитом.
4. **Создать commit**: `chore: release v<new>` с пустым телом. НЕ использовать
   `--amend` и `--no-verify`.
5. **Создать annotated git tag**: `git tag -a v<new> -m "Release v<new>"`.
   Тег ТРЕБУЕТСЯ делать annotated, а не lightweight — agloom при
   разрешении `#v<new>` ссылок ожидает именно аннотированные теги.
6. **Push**: `git push origin main` и затем `git push origin v<new>`.
   Раздельный push снижает риск оставить тег без коммита при сбое сети.
7. **Создать GitHub Release**: `gh release create v<new> --title "v<new>"
--notes "<release-notes>"`. Если `gh` недоступен — попросить
   пользователя создать релиз вручную и передать URL.
8. **Верифицировать**: `gh release view v<new>` возвращает корректный tag
   и assets (если есть).

## Definition of Done

Релиз завершён когда:

- `dod-1`: `plugin.yml` содержит новую версию, закоммичен в `main`.
- `dod-2`: Annotated-тег `v<new>` существует локально и на `origin`.
- `dod-3`: GitHub Release опубликован и доступен по прямой ссылке.
- `dod-4`: Consumer-проект МОЖЕТ подтянуть плагин по новой ссылке:
  `git@github.com:cusxy/skill-cycling#v<new>` (проверка — ответственность
  пользователя, скиллу ТРЕБУЕТСЯ напомнить об этом в сводке).
- `dod-5`: Сводка результатов выведена.

## Обработка ошибок

- **DoR-1/2/3 не пройден** (грязное дерево, не `main`, отставание от
  upstream): прекрати выполнение и попроси пользователя привести репозиторий
  в валидное состояние. НЕ делай `git stash`, `git reset --hard`, принудительные
  `checkout` — это необратимые действия над пользовательской работой.
- **Конфликт при push**: кто-то запушил в `main` параллельно. Прекрати,
  попроси пользователя сделать `git pull --rebase` и перезапустить skill.
  НЕ использовать `--force` к `main`.
- **Тег уже существует**: проверь, опубликован ли релиз. Если да — версия
  уже занята, запроси у пользователя следующий bump. Если нет — попроси
  пользователя удалить локальный/удалённый тег вручную и перезапусти шаги
  с п. 5.

## Сводка

После успешной публикации ТРЕБУЕТСЯ вывести:

- Номер новой версии и тип bump'а.
- Ссылку на GitHub Release.
- Строку для подключения в consumer-проекте:
  `plugins: [git@github.com:cusxy/skill-cycling#v<new>]`.
- Напоминание пользователю проверить установку в consumer-проекте.
